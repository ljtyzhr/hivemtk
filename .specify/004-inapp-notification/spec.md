# Feature Specification: 站内消息通知模块

**Feature Branch**: `004-inapp-notification`
**Created**: 2026-10-22
**Status**: Draft
**Input**: User description: "设计，开发并发布线上服务器一套完整站内消息通知模块，平台端发布消息，用户端所有人收到通知，查看详情"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 平台运营方发布公告并投递给全体用户 (Priority: P1)

平台运营方在平台运营后台填写标题、正文、级别（普通/警告/重要/成功）与投放对象
（全体租户或指定若干租户），提交后消息进入待投递队列；用户端各租户的成员在
下一次同步周期内收到这条消息，出现在其通知中心与顶部铃铛未读角标中。

**Why this priority**: 这是整个模块的存在理由。没有"平台发→用户收"的投递链路，
其余功能都无从谈起；同时它独立可交付——只实现发布与投递，用户端就已经有了价值。

**Independent Test**: 在平台后台发布一条"全体"消息，等待一个同步周期后，用任一
普通租户成员的账号登录用户端，打开通知中心能看到该条消息标题与正文，铃铛角标未读数 +1。

**Acceptance Scenarios**:

1. **Given** 平台运营方已登录运营后台，**When** 填写标题与正文、级别选"警告"、
   投放对象选"全体租户"并提交，**Then** 发布成功提示出现，消息列表新增一条记录，
   状态显示为已发布并记录发布时间。
2. **Given** 一条已发布的全体消息，**When** 任意租户的成员打开用户端通知中心，
   **Then** 该消息出现在列表中，类型标签显示为"警告"，且携带发布时间。
3. **Given** 一条已发布的全体消息，**When** 多个不同租户的成员分别打开通知中心，
   **Then** 每个租户都能看到该消息，且彼此的数据互不可见（租户 A 看不到租户 B 的消息）。

---

### User Story 2 - 指定租户定向投放 (Priority: P2)

平台运营方选择若干指定租户作为投放对象，发布后只有这些租户的成员收到消息，
其他租户完全看不到。

**Why this priority**: 定向投放是运营场景的常见需求（针对试点租户发布、
针对特定客户群发通告），但"全体投放"已覆盖主链路，故列 P2。

**Independent Test**: 发布一条只投给租户甲的消息，验证租户甲成员能看到、
租户乙成员看不到。

**Acceptance Scenarios**:

1. **Given** 平台运营方选择租户甲、租户乙为投放对象，**When** 发布消息，
   **Then** 该消息在租户甲与租户乙的通知中心可见。
2. **Given** 一条仅投给租户甲的消息，**When** 租户乙的成员打开通知中心，
   **Then** 该消息不出现在其列表与未读数中。

---

### User Story 3 - 用户查看消息详情并标记已读 (Priority: P1)

用户在用户端通知中心点击一条消息，弹出详情展示完整标题、正文、级别、发布时间与
可选跳转链接；标记已读后，该条消息在**该用户**自己的列表与角标中转为已读，
不影响其他用户各自的未读状态。

**Why this priority**: "查看详情"是用户需求的显式表述；"按人独立已读"是本模块
的关键语义——若做不到这一点，一人点开会替所有人清掉未读角标，功能即失效。

**Independent Test**: 用户甲点开消息详情并标记已读，验证甲的角标减 1、
消息显示已读；同时用用户乙的账号查看同一消息，仍显示未读。

**Acceptance Scenarios**:

1. **Given** 用户有一条未读消息，**When** 点击该消息，**Then** 弹出详情窗口完整
   展示标题、正文、级别标签、发布时间，若消息带链接则同时提供可点击的跳转入口。
2. **Given** 用户甲点击一条未读消息的详情，**When** 详情窗口打开且消息标记为已读，
   **Then** 用户甲的通知中心中该条显示已读，其铃铛角标未读数减 1。
3. **Given** 用户甲已读某条消息，**When** 用户乙查看同一消息，
   **Then** 用户乙的列表中该条仍为未读，角标不受甲的操作影响。
4. **Given** 用户有多条未读消息，**When** 点击"全部标记已读"，**Then** 该用户的
   所有消息转为已读，未读数归零。

---

### User Story 4 - 实时感知新消息 (Priority: P2)

用户停留在用户端任意页面时，顶部铃铛的未读角标自动更新，收到平台新消息时
无需手动刷新即可看到提示。

**Why this priority**: 角标是通知模块的"门面"，当前线上角标恒为 0（从未被赋值），
属功能缺失。但它的价值依赖前三个故事先成立，故列 P2。

**Independent Test**: 保持用户端页面打开，平台发布一条消息，在同步周期内观察
铃铛角标数字出现并增长。

**Acceptance Scenarios**:

1. **Given** 用户已登录且停留在用户端任意页面，**When** 平台发布了新消息，
   **Then** 铃铛角标在同步周期内更新为新的未读数。
2. **Given** 用户没有未读消息，**When** 停留在用户端，**Then** 铃铛不显示角标数字。

---

### Edge Cases

- **平台不可达**：用户端同步时平台返回错误或超时 —— 保留上一次的已投递消息，不清空、
  不报错中断；用户端一切照常可用（仅新消息延迟到达）。
- **平台未接入**（平台联动关闭的纯离线部署）：用户端不发起任何平台请求，
  通知中心仅显示本地产生的业务通知，不产生任何错误日志噪音。
- **重复投递**：同一平台消息被拉取多次（网络重试、周期重叠）——用户端不得产生
  重复行，用户只会看到一条。
- **消息在投递后被撤回/删除**：平台删除该消息后，用户端已投递的副本仍可查看
  （以投递时的快照为准），但不再重复投递。
- **发布内容为空或超长**：标题为空、正文为空、或超出长度上限 —— 平台端拒绝发布
  并给出明确提示，不产生半条消息。
- **同一租户多成员同时上线**：多个成员同时拉取同一条消息 —— 不产生重复行。
- **用户在消息送达前进入通知中心**：看到的是上一次投递的结果，不报错、不空白页。
- **平台消息与本地业务通知并存**：通知中心同时列出两类消息，来源可区分，
  平台消息可按级别筛选。

### Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 平台运营方 MUST 能在运营后台发布消息，字段包含标题、正文、级别、投放对象。
- **FR-002**: 标题与正文 MUST 非空；平台端 MUST 在校验失败时拒绝发布并给出明确提示。
- **FR-003**: 级别 MUST 取值为 普通 / 警告 / 重要 / 成功 四档之一，默认"普通"。
- **FR-004**: 投放对象 MUST 支持"全体租户"与"指定租户集合"两种形态；指定形态下
  未被指定的租户 MUST 收不到该消息。
- **FR-005**: 平台端 MUST 记录每条消息的发布时间，投递方据此增量拉取。
- **FR-006**: 用户端 MUST 能按租户维度取到面向自己的消息；租户之间 MUST 互相隔离。
- **FR-007**: 用户端 MUST 对同一平台消息只保留一条投递副本，重复拉取 MUST 幂等。
- **FR-008**: 用户端 MUST 在平台不可达时保留既有消息，不清空、不报错中断。
- **FR-009**: 用户端 MUST 在平台联动关闭时完全跳过投递环节，不产生平台请求与错误日志。
- **FR-010**: 通知中心 MUST 列出消息，支持按级别、已读状态、关键词筛选与分页。
- **FR-011**: 用户 MUST 能查看单条消息详情（完整正文、级别、发布时间、可选跳转链接）。
- **FR-012**: 平台消息的已读状态 MUST 按用户独立记录 —— 一人已读 MUST NOT 影响他人。
- **FR-013**: 用户 MUST 能将单条消息标记为已读，以及将自身全部消息标记为已读。
- **FR-014**: 未读数 MUST 与用户自己的已读记录一致，MUST NOT 使用全局共享的已读位。
- **FR-015**: 铃铛角标 MUST 反映当前用户的未读数，并在有新消息时自动更新。
- **FR-016**: 本地产生的业务通知（待办超时、待审核等）MUST 保持现有行为与可见性不受影响。
- **FR-017**: 平台消息与本地业务通知 MUST 在通知中心共存，并可按来源区分。
- **FR-018**: 平台消息 MUST NOT 出现在其他租户的通知中心，即使直接构造请求参数。
- **FR-019**: 系统 MUST 记录每条消息的投递结果（成功/失败/跳过），供运营方追溯。
- **FR-020**: 消息正文 MUST 以纯文本呈现，MUST NOT 解释为可执行内容。

### Key Entities

- **平台消息（Platform Message）**：平台运营方发布的一条通知。属性含唯一标识、
  标题、正文、级别、投放对象、发布时间、创建人。
- **通知（Notification）**：送达用户端的、某租户可见的一条消息副本。
  属性含唯一标识、所属租户、来源平台消息标识、类型、级别、标题、正文、跳转链接、创建时间。
- **通知回执（Notification Receipt）**：某用户对某条通知的已读记录。
  属性含通知标识、用户标识、已读时间。一个通知可对应多条回执（每人一票）。
- **租户**：消息的投放与隔离维度。平台消息可面向全体租户或指定租户集合。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 平台运营方在后台完成一次发布到全体用户可见，全程不超过 2 分钟。
- **SC-002**: 平台消息发布后，用户端在 5 分钟内对全体租户成员可见。
- **SC-003**: 消息已读状态在用户之间完全隔离——任意一名用户标记已读后，
  其他用户的未读数变化量为 0。
- **SC-004**: 用户端在平台不可达时，通知中心的可用性不下降，现有消息一条不少。
- **SC-005**: 用户从打开通知中心到读完一条消息详情，不需要超过 3 次点击。
- **SC-006**: 消息投递不产生重复行——同一条平台消息在任一租户的通知中心中至多出现一次。
- **SC-007**: 平台消息不跨租户泄露——任一租户成员均无法看到其他租户的消息。
- **SC-008**: 平台联动关闭的部署形态下，用户端不向平台发起任何请求。

## Assumptions

- 复用现有用户端通知中心页面与顶部铃铛位置，不新增导航入口。
- 复用现有平台运营后台的菜单与权限体系（平台超管可发布）。
- 消息投递采用用户端周期拉取方式（与平台已有的模块下发同步同一模式），
  不引入平台主动回调用户端；生产为单机部署，用户端无公网回调地址。
- 投递周期为 3 分钟（与平台心跳上报节奏一致），以延迟换平台侧零改动风险。
- 租户短码（tenant code）是平台与用户端之间已有的、逐租户唯一的标识，
  平台的租户登记表与用户端的租户表已按此短码一一对应。
- 已读语义采用"平台消息按人独立记录"；本地业务通知沿用其现有的全局已读位，
  本次不改动其语义，避免影响待办 SLA 等既有生产者。
- 用户身份沿用现有登录态与租户绑定，用户端无需新增认证机制。
- 本次不覆盖移动端（uni-app）通知展示，仅覆盖 Web 管理端。
- 消息正文按纯文本处理，不引入富文本渲染能力。
- 存量已投递的本地业务通知不做迁移，保持原样。
