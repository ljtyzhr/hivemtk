# Feature Specification: SaaS 多租户与离线单机双形态一体化

**Feature Branch**: `001-saas-multi-tenant`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "项目 hivemtk 下 user-web user-server 执行 SaaS 架构演变，多租户演变。目的：支持多租户使用，线上版本提供用户一键开户使用，减少用户使用门槛；同时支持本地部署单机版，为需要私域离线部署的用户提供服务。多租户需补全登录注册、完整数据隔离（含后台非 UI 场景防串联）、基于租户 ID 隔离且不入侵业务代码；单租户与多租户一套代码同功能；bridge 等模块同样支持双形态，离线版使用默认租户 ID 维持全部逻辑。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 离线部署用户零感知升级 (Priority: P1)

一位私域离线部署的存量商户，将系统升级到新版本。他不需要做任何配置或数据迁移操作，登录工作台后所有客户、会话、SOP、知识库、报表数据与升级前完全一致，所有功能行为不变。系统从此处于"单租户模式"，数据全部归属默认租户。

**Why this priority**: 这是项目的基本盘。存量开源用户与私域客户的体验绝不能因 SaaS 演进而被破坏；若存量用户升级出问题，商业运营将失去信誉根基。

**Independent Test**: 在装满数据的旧版本实例上升级，逐模块抽查数据完整性与功能回归，全部通过即独立成立。

**Acceptance Scenarios**:

1. **Given** 存量单机版实例含客户/会话/SOP/知识库等历史数据，**When** 升级到新版本并以原账号登录，**Then** 各模块列表、明细、统计与升级前一致，无数据丢失或不可见。
2. **Given** 单机模式下系统运行，**When** 后台定时任务、自动回复、消息入站出站全链路运行一个完整周期，**Then** 行为与升级前一致，无功能降级。
3. **Given** 单机模式，**When** 访问租户自助注册入口，**Then** 该入口不可用（响应明确拒绝），仅保留安装向导与管理界面的账号管理。

---

### User Story 2 - 商家自助一键开户 (Priority: P1)

一位线上访客对产品感兴趣，在 SaaS 站点打开注册页，填写基本信息（企业/团队名、管理员账号、密码）完成注册，即刻获得一个独立的租户空间并自动登录，可直接开始使用产品（建知识库、接渠道、看工作台）。

**Why this priority**: "一键开户、降低门槛"是 SaaS 转型的核心商业目标，注册转化直接决定获客。

**Independent Test**: 从注册页走完整流程到登录进工作台，全程无需人工干预即可验证。

**Acceptance Scenarios**:

1. **Given** SaaS 模式运行中，**When** 访客提交注册表单（合法输入），**Then** 系统创建独立租户与管理员账号，注册人自动登录进入工作台，可正常使用全部基础功能。
2. **Given** 注册表单，**When** 提交不合法输入（缺字段、弱密码、重复账号等），**Then** 明确报错且不产生任何半成品数据（无孤立租户或账号）。
3. **Given** 同一用户名已被其他租户使用，**When** 新租户注册时填写该用户名，**Then** 注册成功（租户之间账号命名空间互不影响，按租户维度唯一）。
4. **Given** 高频恶意注册行为，**When** 同一来源短时间大量提交注册，**Then** 被限流拦截，正常注册不受影响。

---

### User Story 3 - 租户数据完全隔离 (Priority: P1)

两个不同租户同时使用 SaaS 版。租户 A 的管理员只能看到、操作自己租户的数据：客户、会话、渠道账号、SOP、知识库、报表、AI 配置等；任何操作（查询、列表、详情、修改、删除、导出）都无法触达租户 B 的数据。包括所有后台自动运行的流程（定时任务、自动回复、渠道消息入站出站、队列投递）在内，租户之间互不串联。

**Why this priority**: 数据隔离是 SaaS 的生命线，任何一次跨租户数据泄漏都是不可接受的事故。

**Independent Test**: 建立两个租户各写入标记数据，逐 API、逐后台流程交叉验证可见性边界。

**Acceptance Scenarios**:

1. **Given** 租户 A 与租户 B 各自录入客户与会话，**When** 租户 A 用户查询列表、按 ID 直查详情、导出数据，**Then** 结果仅含租户 A 数据；直接伪造请求访问租户 B 的资源 ID 被拒绝（表现为不存在）。
2. **Given** 租户 A 配置了渠道账号（如 Telegram/企微），**When** 该渠道消息入站触发自动回复与后台流程，**Then** 处理过程与产出（回复、工单、标签、SOP 执行）只作用于租户 A 的数据。
3. **Given** 两个租户同时运行定时任务与自动化流程，**When** 后台批量作业执行，**Then** 每个租户的作业处理各自的数据，产出（消息发送、评分、报表）互不混入。
4. **Given** 访客通过嵌入客服组件发起会话，**When** 会话建立与消息收发，**Then** 该访客数据归属且仅归属其对应的租户。
5. **Given** 任一后台流程处理一条排队任务（延时发送、超时恢复等），**When** 任务被消费执行，**Then** 执行使用的上下文与数据边界与任务产生时的租户一致。

---

### User Story 4 - LLM 双轨：用平台的或自带 (Priority: P2)

新注册租户未配置任何 AI 服务即可使用智能回复、RAG 检索等 AI 能力（默认使用平台提供的公共模型池）。有特殊需求的租户（如需要更强模型、或合规要求用自建模型）可在管理界面配置自己的模型服务地址与密钥，配置后其租户内的 AI 能力切换为使用自有模型；未配置或配置失效时回退平台池，业务不中断。

**Why this priority**: 是 SaaS 可用性的体验项（默认即用）与增值项（自带模型）的结合，依赖隔离地基（Story 3）完成。

**Independent Test**: 新租户零配置发起 AI 对话成功；再配置自有模型地址后对话走自有服务；删除配置后回退平台池。

**Acceptance Scenarios**:

1. **Given** 新注册租户未做任何 AI 配置，**When** 其访客发起会话触发 AI 自动回复，**Then** 回复成功产出（使用平台公共模型池）。
2. **Given** 租户管理员配置了自有模型服务，**When** 租户内触发 AI 能力，**Then** 调用指向租户自有服务，且不影响其他租户的模型选择。
3. **Given** 租户自有模型服务故障，**When** AI 能力被调用，**Then** 按既定回退策略降级（回退平台池或明确报错），不产生跨租户影响。
4. **Given** 租户 A 与租户 B 配置了不同模型，**When** 并发使用，**Then** 各自调用各自的模型与用量统计，互不串用。

---

### User Story 5 - 租户内管理与存量管理一致 (Priority: P2)

SaaS 租户的管理员在管理界面完成日常管理：成员账号的增删改、角色与数据范围分配、系统参数调整——操作体验与离线版管理员一致（同一套管理界面、同一套逻辑，仅数据边界限定在自己租户内）。

**Why this priority**: 保证两形态功能对齐（"单租户和多租户一样的功能"），降低维护与文档成本。

**Independent Test**: 在两形态下执行同一组管理操作，行为与结果一致（数据边界除外）。

**Acceptance Scenarios**:

1. **Given** SaaS 租户管理员，**When** 创建成员账号、分配角色与数据范围，**Then** 成员仅能登录本租户、仅能访问本租户数据。
2. **Given** 同一组管理操作分别在单机版与 SaaS 版执行，**When** 对比结果，**Then** 行为一致（单机版无租户维度显示差异）。

---

## Edge Cases

- 存量数据升级：升级时已有数据的归属自动归入默认租户，要求升级过程幂等、可中断续跑。
- 用户名跨租户冲突：同一用户名在不同租户可并存；登录必须无歧义（通过全局唯一标识如邮箱，或明确的租户标识输入）。
- 未携带身份的入口（渠道回调、访客请求）：必须能从请求自带线索（账号标识、渠道凭证）唯一解析出租户；解析失败时拒绝处理并告警，绝不落入"默认租户"。
- 后台流程无请求上下文：所有自动任务以任务数据自身携带的租户归属为准；数据未携带归属的任务被视为异常数据，拒绝执行并告警。
- 租户停用/欠费（预留）：租户状态非正常时，其用户登录受限、后台任务跳过该租户；数据保留不删除。
- 系统级操作（数据备份、恢复、升级迁移）：以系统身份运行，不归属任何租户，操作对象覆盖全库但仅限系统入口触发。
- 越权试探：伪造他人租户的资源 ID、伪造回调凭证、重放访客令牌，均以"不存在/拒绝"响应并记录安全审计。
- 性能隔离：单租户数据量增长不得显著拖慢其他租户的查询（行级隔离下靠索引与查询模式保障，需验收基准）。

## Requirements *(mandatory)*

### Functional Requirements

**双形态开关与兼容**

- **FR-001**: 系统 MUST 支持两种部署形态：多租户 SaaS 模式与单租户离线模式，由部署配置一项开关决定，同一份代码产物。
- **FR-002**: 离线模式下，系统 MUST 将全部数据（存量与新增）归属到唯一默认租户，用户无感知，功能与 SaaS 模式对齐（除注册与租户管理入口）。
- **FR-003**: 离线模式下 MUST 禁用租户自助注册入口；账号管理仅通过安装向导与管理界面。
- **FR-004**: 存量实例升级 MUST 自动完成数据归属初始化，过程幂等，失败可重试。

**注册与身份**

- **FR-005**: SaaS 模式 MUST 提供自助注册：填写企业/团队名与管理员凭证即可创建新租户并自动登录。
- **FR-006**: 注册 MUST 有防滥用措施（频率限制），且注册过程原子（不产生半成品租户）。
- **FR-007**: 用户身份 MUST 在租户内唯一；登录 MUST 在跨租户场景下无歧义（支持全局唯一标识登录；单机模式保持现有登录方式不变）。
- **FR-008**: 会话凭证 MUST 携带租户归属；无归属凭证的受保护请求 MUST 被拒绝。
- **FR-009**: 每个租户 MUST 拥有唯一租户标识，用于数据归属与外部入口（回调 URL、嵌入组件）的租户定位。

**数据隔离**

- **FR-010**: 所有业务数据 MUST 携带租户归属；数据读取与写入 MUST 自动限定在当前上下文租户内，业务功能代码不得各自手工处理隔离逻辑。
- **FR-011**: 隔离机制 MUST 在框架层统一实施（数据访问层强制约束），并 MUST 在上下文缺失租户时拒绝服务（宁可报错，不可默认全量）。
- **FR-012**: 全部非 UI 自动流程（定时任务、队列、回调、事件驱动流程）MUST 以数据自带租户归属执行；系统 MUST 提供统一的租户遍历机制让周期性任务覆盖所有活跃租户。
- **FR-013**: 全局性数据（系统配置、字典、平台心跳等少数清单）MUST 显式登记为"无租户归属"清单并集中管理；清单之外默认一律视为租户数据。
- **FR-014**: 数据访问 MUST 统一走单一形态的约束通道；MUST 清除绕过统一通道的直连式数据访问历史债务，并以自动化检查永久防止其回归。
- **FR-015**: 缓存键、队列键、文件存储路径、导出文件等衍生资源 MUST 按租户分域，防串读串写。

**外部入口与渠道**

- **FR-016**: 渠道回调与访客入口 MUST 依据请求自带线索解析租户；解析失败的请求 MUST 被拒绝并告警。
- **FR-017**: 嵌入客服组件 MUST 能按租户定位会话归属；访客令牌 MUST 绑定租户。
- **FR-018**: 实时推送通道（消息推送、看板流）MUST 按租户分域，租户用户仅收到本租户事件。

**AI 能力**

- **FR-019**: 平台 MUST 提供公共模型池作为未配置租户的默认 AI 服务；租户 MUST 可配置自有模型服务并即时生效。
- **FR-020**: 模型服务选择 MUST 按租户隔离（配置、调用、熔断降级、用量统计互不影响）；租户未配置或配置失效时按策略回退公共池。

**管理界面**

- **FR-021**: 前端 MUST 适配双形态：SaaS 模式提供注册页与租户上下文展示；离线模式隐藏注册入口，界面保持现状。
- **FR-022**: 多租户模式下 MUST 提供租户维度的运营可见性（租户清单、状态、活跃度）供平台运营方管理使用。

### Key Entities *(include if feature involves data)*

- **租户（Tenant）**: SaaS 中的独立经营主体；拥有唯一标识、名称、状态（正常/停用）；是几乎所有业务数据的归属根。
- **租户用户（SystemUser）**: 租户内可登录的操作者；属于唯一租户；用户名租户内唯一；保留既有角色与数据范围体系（其语义被限定在租户边界内）。
- **业务数据（客户/会话/渠道账号/SOP/知识库/报表等全部既有实体）**: 全部携带租户归属属性；归属在创建时由上下文自动确定。
- **模型服务配置（LLM Provider）**: 租户可自定义的 AI 服务配置；含平台公共池（无租户归属）与租户自有配置两层。
- **访客（Visitor）与渠道账号（Channel/Bridge Account）**: 请求线索的载体，是外部入口解析租户的依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 存量离线实例升级后，全量既有自动化测试通过率 100%（行为无回归），人工抽查核心模块数据完整性无差异。
- **SC-002**: 两租户交叉越权测试中，跨租户数据读取/写入成功率为 0%（覆盖全部业务域列表/详情/写操作与全部后台自动流程）。
- **SC-003**: 新访客从打开注册页到进入可用的独立工作台，全程自助完成，耗时 ≤ 1 分钟，成功率 ≥ 99%（排除恶意拦截）。
- **SC-004**: 新租户零配置发起 AI 会话首响应成功率与存量单机版持平；配置自有模型后调用 100% 指向自有服务。
- **SC-005**: 单机模式与 SaaS 模式功能清单一致率 100%（除注册/租户运营管理两个专属入口外）。
- **SC-006**: 后台周期任务在多租户环境下运行一个完整周期后，各租户产出的数据归属正确率 100%（无串联）。
- **SC-007**: 统一数据访问约束的自动化检查纳入持续集成门禁，绕过通道的历史债务清零（业务代码 0 处直连式访问）。

## Assumptions

- 租户物理形态采用共享库 + 行级租户标识隔离（已论证：245 表规模下成本与风险最优）；数据库层行级安全策略（RLS）作为二期可选加固，不阻塞本期。
- "平台提供 LLM"首期以平台公共模型池（预置于 SaaS 环境的默认模型配置）实现；平台端统一网关计费转发不在本期范围。
- 开户入口首期为系统内自助注册；平台端（hivemtk-platform）计费、订阅、开户下发能力可后续叠加，接口留有扩展位。
- 存量数据全部归属默认租户（默认租户 ID 固定）；不做存量数据的租户拆分。
- 原生 SQL 历史债务（业务数据访问中的直连式写法）纳入本次彻底清偿范围，迁移类 DDL 除外。
- 数据库层面的强制安全加固（如数据库行级安全策略）作为二期增强项，本期以框架层统一约束 + 全量越权测试 + CI 门禁构成防线。
