## 0. 结论先行（TL;DR）

1. **必须做**。平台承载的是"商户 → 终端用户"的对话内容，一旦出现涉政/涉黄/诈骗/违禁品内容，
   责任落在**平台运营方**（本仓是自部署 SaaS，平台自己运营）。这不是产品功能，是经营资质问题。
2. **主力用离线词库，不用云 API 做主链路**。理由有三条，且都是本项目特有的：
   - 本仓硬性约束是「数据零出域」（`CLAUDE.md` 规则 4.3）：把用户原文发给第三方审核云，
     是把最敏感的数据挪出部署边界，需要客户逐家同意，SaaS 多租户下不可行；
   - 审核是**每条消息都要跑**的动作，云 API 按条计费 + 网络 RTT，会直接变成产品成本与延迟；
   - 云 API 的结论不能单独承担"冻结某个人 24 小时"这种处置，因为它不可解释、不可本地复核。
3. **外部 API 保留为"显式开启的增强项"**（双重开关：环境变量 + 策略行），默认一个请求都不发。
4. **异步化**：业务链路只做一次单行插入，审查在 worker 里跑。首响与 LLM 流式输出与审查完全解耦。
5. **处置分主体**：终端用户（`user`）与商户（`merchant`）走**两套不同阈值/动作/时长**，
   因为两者能被处置的东西根本不同（用户可拒收其消息；商户只能拦其发布内容、冻结其经营能力）。
6. **差距是明确的**（见 §7）：入口侧真正"拒绝入库"、繁简/形近字归一化、云厂商签名适配、
   管理前端页面，都不在本次范围，已逐条列出并给了后续方案。

## 1. 法律与合规依据

面向中国大陆运营，内容安全不是"最佳实践"，而是有明确法条与处罚先例的义务。

| 依据 | 条款要点 | 对本产品的直接约束 |
|------|----------|--------------------|
| 《网络安全法》 | 第二十一条：采取监测、记录网络运行状态与网络安全事件的技术措施，**留存相关网络日志不少于六个月** | 审查记录（谁、什么时候、什么内容、什么结论、谁处置的）必须可查、可留存 ≥ 6 个月 |
| 《网络安全法》 | 第四十七条：发现法律、行政法规禁止发布或传输的信息，应当**立即停止传输**、采取消除等处置措施、保存有关记录、并向主管部门报告 | 需要"停传 + 留证 + 可上报"三件套，缺一不可 |
| 《互联网信息服务管理办法》 | 第十五/十六条：九类禁止内容；发现后停止传输、保存记录、报告 | 禁止内容清单 = 词库分类的初始依据 |
| 《网络信息内容生态治理规定》 | 第十一条：不得制作、复制、发布违法信息；平台需建立**内容审核**与**应急处置**制度 | 需要"审核 → 处置 → 申诉/复核"闭环，不是只做拦截 |
| 《生成式人工智能服务管理暂行办法》 | 第九/十四条：提供者承担网络信息内容生产者责任；发现违法内容应停止生成、停止传输、采取整改措施 | Agent 的**出站回复**与**知识库导入**同样属于审查范围，不能只审用户输入 |
| 《个人信息保护法》 | 最小必要、告知同意、不得超范围对外提供 | ① 审查记录只存脱敏片段（不搬原文）；② 默认不把原文外发第三方（= 外部 API 默认关闭） |

**结论**：至少要覆盖"入站用户消息 + 出站 Agent 回复 + 商户内容资产（素材/知识库/营销文案）"四类文本，
并且必须留下可追溯的处置记录（含操作人、时间、依据、申诉结果）。

## 2. 技术方案全景（三层）

业界通行的内容审核是分层漏斗，不是单点。本仓按同样的分层实现，**每层的定位不同**：

| 层 | 手段 | 延迟 | 能查什么 | 查不到什么 | 本项目取舍 |
|----|------|------|----------|------------|------------|
| **L1 离线词库** | 归一化 + Aho–Corasick 多模式匹配 | 微秒级 | 明确词条（违禁品、辱骂、广告用语、自定义） | 变体语义、含蓄表达、图片/语音 | ✅ 主力，进程内快照 |
| **L2 策略裁决** | 严重级别 → 阈值 → 动作/处置 | 纳秒级 | "命中该不该拦、拦了怎么罚" | —— | ✅ 主体差异化策略 |
| **L3 外部审核 API** | 云厂商/自建大模型审核 | 数十~数百毫秒 | 语境、隐喻、变体、图片/OCR | 不可解释、成本、数据出域 | ⚠️ 默认关闭，抽样开启 |
| （L4） | 人工复核 | 分钟~小时 | 争议判定、误杀纠正 | 时效 | ✅ 入队 + 改判连带解除 |

### 2.1 L1：为什么必须是"归一化 + AC 自动机"

**归一化**（`internal/contentguard/normalize`）处理的不是词库大小，而是**变体规避**——
真正让词库失效的是下面这些 10 行代码就能写出来的绕法：

| 规避方式 | 例子 | 归一化动作 |
|----------|------|------------|
| 插入分隔符 | `敏 感 词` / `敏*感*词` / `敏-感-词` | 丢弃空白/标点/符号 |
| 全角 | `ＡＢＣ` / `１２３` | 全角 ASCII 折叠为半角 |
| 零宽字符 | `敏\u200b感\u200c词` | 丢弃 ZWSP/ZWJ/BOM/软连字符 |
| 大小写 | `SeNsItIvE` | 折叠为小写 |

三条设计约束（缺一条就引入新问题）：

1. **索引可回映射**：归一化后每个 rune 记住它在原文的位置，审查记录里才能贴出"原文哪一段被命中"。
   给运营看一段被抹掉标点的文本，等于让人自己猜原文。
2. **不做语义猜测**：只做确定性的字符级变换。繁→简、拼音、形近字这类需要大词表的变换留给 L3，
   本地做不准会把误杀率推高，而误杀成本由业务方承担。
3. **词条与文本用同一套归一化**：否则出现"词库有这个词但永远不命中"（两边坐标空间不一致）。

**匹配器**（`internal/contentguard/matcher`）用 AC 自动机，不是逐词 `strings.Contains`：

| | 朴素子串（现状 `internal/safeprompt`） | AC 自动机（本功能） |
|---|---|---|
| 复杂度 | O(词数 × 文本长度) | O(文本长度 + 命中数) |
| 1 万词 × 200 字消息 | 200 万次子串比较 | 200 次状态转移 |
| 命中位置 | 通常"找到第一个就返回" | 一遍扫描拿到全部命中区间 |
| 可局部抑制 | ✗（拿不到区间） | ✓（白名单按区间重叠抑制） |

命中位置是白名单与证据链的前提：没有区间就只能整条放行或整条拦。

### 2.2 L2：为什么阈值必须分主体

同一级别（例如 severity=2）在两个主体上的正确动作**不同**：

| 维度 | `user`（终端用户/访客） | `merchant`（商户/租户） |
|------|------------------------|--------------------------|
| 审什么 | 只审 `inbound_message` | 审 `material` / `kb_document` / `outbound_reply` / `marketing_copy` |
| 拦截阈值 | severity ≥ **3**（聊天误杀成本高，中危只转人工） | severity ≥ **2**（对外内容发出即收不回） |
| 拦截动作 | `reject`（该条消息不生成回复） | `block_publish`（内容不予发布/下发） |
| 临时冻结 | 24 小时 | 7 天 |
| 永久升级 | 窗口内第 **3** 次拦截 | 窗口内第 **2** 次拦截 |

理由：商户是经营主体，其对外发布的内容直接影响平台合规责任，处置权在平台运营方；
终端用户的一次口无遮拦则是常态，一次就永久封禁的误杀代价远大于收益。

### 2.3 L3：外部审核 API 的取舍

厂商与价格（2026 年公开报价，用于判断"要不要买"，不作为接入契约）：

| 厂商 / 产品 | 计费 | 折合单价（约） | 备注 |
|-------------|------|----------------|------|
| 阿里云内容安全（文本反垃圾） | 1.8 元 / 千条 | ≈ 0.0018 元/条 | 有免费额度；支持自定义词库；有 SDK |
| 阿里云内容安全（大模型版） | 0.31–0.6 美元 / 千次 | ≈ 0.0022–0.0043 元/条 | 语境理解更强，成本高一个量级 |
| 腾讯云天御（文本内容安全） | 25 元 / 万条，含 3000 条免费额度 | ≈ 0.0025 元/条 | 需签名（TC3-HMAC-SHA256） |
| 网易易盾 | 按量/包年，需商务询价 | —— | 主打社区内容，有私有化部署版本 |

开源方案（可作为**自建审核服务**的实现参考，或用于垫片）：

| 方案 | 形态 | 适用性判断 |
|------|------|------------|
| Qwen3Guard / Llama Guard / ShieldGemma | 审核专用判别模型 | 需要 GPU 与推理服务，单条 10–100ms 级；适合"自有 GPU"的部署形态，不适合默认形态 |
| Karrecy/sensitive-go、kirklin/go-swd | Go 敏感词库（DFA/Trie） | 现成词库 + 匹配实现，可作为内置词库的种子来源 |

**本项目结论**：L3 只作为"客户自己愿意出域"的可选项接入，接口抽象为 `provider.Auditor`，
对接自家网关（推荐）或云厂商代理；真正的云厂商签名适配不在本次范围（见 §7）。

## 3. 架构与数据模型

### 3.1 组件与职责

```
业务链路（webhook / Agent / 商户后台）
        │  只调一次 SubmitReview（单行插入，不扫描、不外呼、不处置）
        ▼
   guard_tasks ──(进程内 notify + 轮询)──► worker（进程内 N 并发）
        │                                      │
        │                                      ├─ L1 Dictionary（AC 快照，按租户）
        │                                      ├─ L2 Evaluate（阈值/动作/升级）
        │                                      ├─ L3 provider.Auditor（可选、抽样）
        │                                      ▼
        │                              guard_records（结论 + 证据 + 复核状态）
        │                                      │
        │                                      ▼
        └──────────────────────────────► guard_sanctions（冻结/黑名单，临时/永久）
```

### 3.2 五张表（全部为租户表，`tenant_id` 走 GORM 隔离 callback）

| 表 | 作用 | 关键约束 |
|----|------|----------|
| `guard_words` | 词库（`deny` 拦截词 / `allow` 白名单词） | `(tenant_id, list_kind, word)` 唯一 |
| `guard_policies` | 审查策略，**按主体类型一行** | `(tenant_id, subject_type)` 唯一 |
| `guard_tasks` | 异步任务队列 | `task_key` 唯一（幂等键），`(status, next_run_at)` 支撑认领 |
| `guard_records` | 审查结论 + 命中证据 + 复核状态 | `hits` 用 JSON 序列化；片段脱敏 |
| `guard_sanctions` | 处置（冻结/黑名单） | 生效判定只看时间，不依赖定时任务 |

设计要点（每条都有具体反例在 ADR-017 里）：

- **白名单与拦截词同表**：白名单是"这个词组里出现该词不算违规"的唯一表达式，独立一张表会让抑制逻辑在两处维护。
- **策略按主体一行而不是"全局策略 + 覆盖"**：合成一张表后每个字段都要问"这一列对另一类主体是什么语义"，
  而语义分叉正是线上误处置的源头。
- **处置与 `model.UserBlacklist` 分表**：后者是坐席"不想再看到这个人"的会话运营动作，
  本表是"命中违规内容"的合规处罚；合并会让两类动作在同一行上互相覆盖。
- **生效判定唯一依据**：`Active=true` 且（`Level=permanent` 或 `ExpiresAt` 在未来）。
  时间判定永远比定时任务可靠（定时任务挂了、进程重启、副本没选上主，判定照样正确）。

### 3.3 为什么不用 `trace_events` 承载审查队列

这是本项目最容易被"复用现有设施"带偏的一处。`trace_events` 是**旁路可观测**数据：
best-effort 写入、队列满即丢、metadata 不含全文。拿它当审查队列，等于把"这个人有没有违规"
建在一条**允许丢失**的通路上。所以：

- 审查任务的真相在 `guard_tasks` 表里，进程重启/发布不丢在途任务；
- 内存 channel 只做"有新活"的**通知**（丢了最多延迟一个轮询周期，不影响正确性）；
- `trace_id` 只做关联与回溯（这条审查属于哪次请求），不承载审查本身。

## 4. 关键行为口径（可直接当验收清单）

| # | 场景 | 期望行为 | 依据 |
|---|------|----------|------|
| 1 | 用户发一条严重违规消息 | 入队 → 结论 `block` / 动作 `reject` / 临时冻结 24h | `service.Evaluate` |
| 2 | 同一用户 24h 内第 3 次被拦 | 升级为**永久**冻结，处置行**不新增**（幂等升级） | `service/sanction.go` |
| 3 | 中危消息（user, sev=2） | 结论 `review`，进人工队列，**不**冻结 | 同上 |
| 4 | 商户营销文案 sev=2 | 结论 `block` / 动作 `block_publish` / 临时冻结 7 天 | 商户策略 |
| 5 | 词库里有白名单词覆盖命中区间 | 抑制该次命中（误杀第一道闸） | `engine.Scan` 区间重叠抑制 |
| 6 | 内容重复提交（同一主体同一内容） | 幂等键去重，不产生第二条任务、不罚两次 | `task_key = sha256(subject_type, subject_id, scene, content)` |
| 7 | 内容超长（> 20000 rune） | 截断审查并标记 `Truncated`，调用方按"超长"处理（不静默 pass） | `MaxScanRunes` |
| 8 | 词库读失败 | **失败开放**（漏审而非全拦）+ 记录里缺 `dict` 源 + 错误留痕 | 拦全量用户比漏审是更大事故 |
| 9 | 策略表读不到 | 回落出厂策略（审查不能因为一次库抖动变成全放行） | `engine.Policy` |
| 10 | 外部审核 API 未配置 | 一个请求都不发 | `provider` 包 + `APIEnabled=false` |
| 11 | 外部 API 超时/非 200/业务码失败 | 降级为仅本地结论，`sources` 不写 `api` | `pipeline.processOne` |
| 12 | 外部 API 判高风险、本地无命中 | 以外部结论为准 → 升级为 `block`（并保留证据） | 同上（`evalHits` 合并） |
| 13 | 任务处理失败且未超次数 | 回 `pending` 并顺延重试（积压数可见） | `MarkFailed(retryAt != 0)` |
| 14 | 任务处理失败且超次数 | 置 `failed` 死信（不留在 pending 里污染积压数） | `MarkFailed(retryAt = 0)` |
| 15 | 人工复核 `overturned` | 改判并**连带解除**自动处置 | 只改记录不解冻，复核按钮等于安慰剂 |
| 16 | 用户在冻结期内继续发消息 | 不再生成 Agent 回复（= 拒收） | `agent_runtime.SetGuardGate` |

## 5. 成本与容量估算

假设：单租户日活 5 万条入站消息，词库 5000 条，平均消息 120 字。

| 项 | 估算 |
|----|------|
| L1 匹配 | 每条 ~5000 状态转移以内，单核 > 20 万条/秒 ⇒ 日 5 万条约 0.25 秒 CPU/天 |
| 词库快照 | 5000 条 AC 自动机约 1–3 MB/租户（含归一化后的 trie），按租户缓存 + 30 秒 TTL |
| 任务表 | 每条任务一行（含全文），按"7 天清理"计算峰值 ≈ 35 万行/租户 |
| 外部 API（若开启 10% 抽样） | 5000 条/天 × 0.0018~0.0025 元 ≈ 9~12.5 元/天/租户 |
| 外部 API（若全量） | ≈ 90~125 元/天/租户 —— 这是"不做全量"的主要原因之一 |

**结论**：L1+L2 的边际成本近乎为零，可以全量跑；L3 必须抽样，否则成本随消息量线性爆炸。

## 6. 运维与运营要求

1. **留痕 ≥ 6 个月**（《网络安全法》第二十一条）：`guard_records` / `guard_sanctions` 只做归档，不做硬删；
   任务表 `guard_tasks.content` 存全文，按 7 天清理（全文不是留证必需，证据在 `guard_records.hits` + 脱敏片段里）。
2. **可上报**：按 trace_id / 主体 / 时间窗导出审查记录的能力是应急处置的前提（当前 API 已支持按维度筛选）。
3. **词库维护流程**：内置词库只做"明显违法"的基线；行业词（涉赌、涉诈、竞品贬损等）由运营按租户配置，
   改动后立即失效快照（`Dictionary.Invalidate`），并有 30 秒 TTL 兜底。
4. **误杀处置流程**：`review` 结论进人工队列 → 复核 `confirmed` / `overturned`；
   `overturned` 必须连带解除处置（实现已强制）。
5. **外部 API 开启前的合规确认**：需要客户书面同意数据出域；开启后建议同时配置主机白名单
   （`CONTENT_GUARD_API_HOSTS`）与强制 HTTPS（非 HTTPS 需显式 `CONTENT_GUARD_API_ALLOW_INSECURE`）。

| # | 差距 | 影响 | 后续方案 |
|---|------|------|----------|
| 1 | **入口侧未做真正"拒绝入库"**：冻结只作用于 Agent 回复链路（`agent_runtime` 闸门），消息本身仍由渠道 webhook 落库 | 被冻结用户的消息仍出现在收件箱，只是不自动回复 | 在渠道适配层（webhook 解包后、入库前）调用 `Runtime.IsBlocked`，命中则丢弃并记 `guard_records`；涉及各渠道适配器，需逐渠道回归 |
| 2 | **繁简 / 拼音 / 形近字未归一化** | 繁体输入（"賭博"）绕不过简体词库 | 词库侧做双向登记（简/繁一对），或引入 OpenCC 字典做确定性映射；语义级变体仍交给 L3 |
| 3 | **云厂商签名适配未实现**（当前是通用 JSON-over-HTTP 契约） | 接阿里云/腾讯云需要中间网关做协议翻译 | 推荐做法就是"自家网关"（一次适配，多租户复用，且便于统一审计）；如需直连再按厂商写适配器 |
| 4 | **管理前端页面未做**（仅后端 API + 文档） | 运营改词库/复核/解冻只能走 API | 前端按 `/api/manage/content-guard/*` 的 15 个端点建页面（词库、策略、记录、处置四个 tab + 新手引导） |
| 5 | **图片 / 语音 / 视频内容未审** | 仅覆盖文本 | 图片走 OCR + L3 图片审核；语音先 ASR 再走文本链路 |
| 6 | **异步窗口内的首条消息可能已被回复** | "不阻塞前端任务"的固有代价：判定是异步的，第一条违规消息可能已经发出去了 | 冻结对**后续**消息生效；若业务上不可接受，可对高危场景（如商户对外发布）改用同步 `ScanNow` 前置校验 |
| 7 | **没有申诉入口**（只有内部人工复核） | 用户侧无法自助申诉 | 申诉单复用 `human_task` 域，`overturned` 触发解冻（链路已具备） |
| 8 | **词库未做分词/歧义处理**（纯子串 + 归一化） | 短词容易误杀（如"杀"命中"杀虫剂"） | 短词（≤2 字）强制要求搭配白名单或升级为"上下文规则"；这是运营口径，不是代码能自动解决的 |
| 9 | **审查任务队列没有查询端点**：`guard_tasks` 的 `failed` 死信只能直查表（`stats` 只报 `pending_tasks`） | 运营看不到"哪些审查没跑成" | 给 `service.TaskStore` 加 `List(ctx, status, limit)`，再挂 `GET /api/manage/content-guard/tasks?status=failed` |

## 8. 与既有实现的对比（为什么另起一套）

| 维度 | `internal/safeprompt`（既有） | `internal/contentguard`（本功能） |
|------|------------------------------|-----------------------------------|
| 定位 | LLM 提示词注入/敏感词前置过滤 | 内容合规审核（判定 + 留证 + 处置） |
| 匹配 | 朴素子串，词库 > 1k 建议换 AC（包注释里自己写了这条备忘） | AC 自动机 + 归一化 |
| 词库 | 进程内 map，注册式，无租户隔离 | 数据库表，按租户，可热更新 |
| 结论 | 只有 `Violation` 列表 | `verdict` / `action` / `freeze_level` / 证据 / 复核状态 |
| 处置 | 无 | 冻结/拉黑（临时/永久），幂等升级，可解除 |
| 复用关系 | `safeprompt.MaskPII` 被本功能用于**记录脱敏** | 不修改 safeprompt 的既有语义 |

两者不是替代关系：`safeprompt` 仍是"喂给 LLM 之前"的护栏，`contentguard` 是"内容是否合规"的判定与处置。
`contentguard` 复用 `MaskPII` 做片段脱敏，避免把手机号/证件号复制进可导出的审查记录表。
