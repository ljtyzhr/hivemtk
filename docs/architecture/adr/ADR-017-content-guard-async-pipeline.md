## 背景

平台是**自部署 SaaS**（平台自己运营），承载"商户 → 终端用户"的对话内容与商户的对外发布内容。
上线至今没有任何内容审核能力，这既是产品缺口，也是法律风险（见调研文档 §1）。

需求侧的四条硬约束（来自业务方，不是技术偏好）：

1. 审核**不能阻塞前端任务**（首响、LLM 流式输出不能被审查拖慢）；
2. **黑名单分两类主体**：基于用户（终端用户）与基于商户（租户）；
3. 用户与商户走**不同规则**（阈值、动作、冻结时长都不同）；
4. 处置要支持**临时冻结 / 永久冻结**。

以及仓库级的硬约束：

5. **数据零出域**（`CLAUDE.md` 规则 4.3）：不得引入"默认把用户原文发给第三方"的路径；
6. 五层架构、控制器禁止 `c.JSON`、测试库需显式 `POSTGRES_TEST_*`（因此核心裁决逻辑必须能离线测）。

## 候选方案与对抗式论证

五条路线都认真过了一遍，**每条都给出"为什么不行/为什么不是首选"的具体反驳**，而不是只列优点。

### 方案 A：只接云厂商内容安全 API（阿里云/腾讯云天御）

- 优点：开箱可用，语境理解强，图片/OCR 一并覆盖，有 SLA。
- **反驳**：
  1. 违反约束 5（数据零出域）。用户原文（可能含手机号、订单号、私密诉求）逐条出域，
     多租户 SaaS 下要每个租户书面同意，不可行。
  2. 成本随消息量线性增长：全量 5 万条/天 ≈ 90–125 元/天/租户（调研 §5）。
  3. 审核是热路径动作，云 API 的 RTT（数十~数百毫秒）× 每条消息，要么拖慢链路，要么必须异步——
     一旦异步，云 API 的"实时拦截"优势就没了，只剩"事后判定"，那它作为主链路的性价比进一步下降。
  4. 结论不可解释：云 API 只给 `risk_level` + 标签，无法回答"命中哪个词、凭什么冻结这个人 24 小时"。
     合规场景恰恰需要可解释的证据链（《网络安全法》四十七条的"保存有关记录"）。
- **结论**：不能作为主力，只能作为可选增强（= 本方案的 L3）。

### 方案 B：只用离线词库（纯本地，完全不接外部）

- 优点：零出域、零 API 成本、微秒级、完全可解释、可本地复核。
- **反驳**：
  1. 词库永远落后于攻防：隐喻、变体、繁简、形近字、新词黑话查不出来。
  2. 对抗性强的场景（涉政、诈骗话术）纯词库命中率会明显下降。
- **反-反驳（为什么仍然选它做主力）**：L1 的价值不是"抓住所有违规"，而是"以零成本抓住绝大多数明确违规，
  并为剩下的一小部分提供**可解释兜底**"。真正的长尾用 L3 抽样补，而 L3 只在客户明确同意出域时开启。
- **结论**：作为主力（L1）成立，但不能只有它。

### 方案 C：复用 `internal/safeprompt` 的现有敏感词实现

- 优点：零新代码，已经在跑。
- **反驳**：
  1. 朴素子串匹配，O(词数 × 长度)，词库上万后每条消息几十万次比较。
  2. 没有命中位置 ⇒ 做不了"白名单按区间抑制"，只能整条放行或整条拦。
  3. 词库是进程内 map + 注册式，没有租户隔离、没有热更新、没有留证与处置。
  4. 它的定位是"喂给 LLM 前的护栏"（提示词注入），不是"内容合规判定"——两件事的验收标准不同。
- **结论**：不复用其匹配器，只复用 `MaskPII`（记录脱敏）。见调研 §8 的对比表。

### 方案 D：同步审核（在业务链路里直接 `Scan` 出结论再返回）

- 优点：结论即时可用，能真正"拦住这一条"。
- **反驳**：违反约束 1。同步审核把以下全部串到用户首响的关键路径上：
  - 词库快照重建（首次或 TTL 到期，要读库）；
  - 策略读取（带 TTL 的库读）；
  - 若开 L3，还要加一次外部 API 的 RTT 与其抖动；
  - 处置写库（冻结/处置行 + 记录行，事务）。
  任一项抖动都变成用户可感知的延迟。更关键的是：**处置本身（冻结谁多久）不该在请求路径里做决策**——
  它要查窗口内历史拦截次数（一次聚合查询），把它塞进热路径是把运营动作的复杂度泄漏给终端用户。
- **结论**：同步只保留"试算"（`/scan` 端点，运营调词库时验证口径），主链路一律异步。

### 方案 E（本方案）：离线词库 + 策略裁决 + 异步流水线 + 可选外部 API + 双主体处置

组合了 A/B/C/D 的可取部分，并针对每条反驳给出对策：

| 反驳点 | 本方案的对策 |
|--------|--------------|
| 词库跑不动（C-1） | AC 自动机：O(长度 + 命中数)，与词库规模解耦（`matcher`） |
| 无位置、无白名单（C-2） | AC 返回全部命中区间 + allow 词按区间重叠抑制（`engine.Scan`） |
| 无租户/无热更新（C-3） | 数据库词库表 + 按租户 AC 快照 + 写入口失效 + 30s TTL 兜底（`service/dictionary.go`） |
| 数据出域（A-1） | L3 默认不构建（`auditor == nil`），双重显式才开（环境变量 + 策略 `api_enabled`） |
| 成本线性爆炸（A-2） | 外部 API 只按策略抽样（`APISampleRate`，默认 0），且抽样是**确定性**的（按内容摘要哈希） |
| 不可解释（A-4） | 证据链存 `guard_records.hits`（词、分类、严重级别、原文区间），片段脱敏后入库 |
| 阻塞前端（D） | 业务链路只做一次单行插入 + 非阻塞通知（`pipeline.Submit`） |
| 队列可靠性 | 队列落库 `guard_tasks`（**不用** `trace_events`，见下文决策四） |

### 被否掉的"看起来更省事"的三个变体

1. **用 `trace_events` 当审查队列** —— 否。它是 best-effort、队列满即丢、metadata 不含全文。
   把"这个人有没有违规"建在允许丢失的通路上是事故设计。→ 专用 `guard_tasks` 表，`trace_id` 只做关联。
2. **用"全局策略 + 主体覆盖"一张表** —— 否。每个字段都要问"这一列对另一类主体是什么语义"，
   而语义分叉正是线上误处置的源头。→ 一主体类型一行（`uni_guard_policy(tenant_id, subject_type)`）。
3. **复用 `model.UserBlacklist` 承载内容处罚** —— 否。那张表是坐席"不想再看到这个人"的会话运营动作，
   本功能是"命中违规内容"的合规处罚；解除条件、审计口径、对上下游影响全不同，合并会让两类动作互相覆盖。
   → 独立 `guard_sanctions`。

## 决策

### 决策一：三层漏斗 + 每层的失败语义各自定义

| 层 | 名称 | 失败时的正确后果 | 理由 |
|----|------|------------------|------|
| L1 | 词库快照 | **失败开放**（这轮查不出违规）+ 记录缺 `dict` 源 + 错误留痕 | 词库挂了就全量拦截，是比漏审更大的事故 |
| L2 | 策略读取 | **回落出厂策略** | 审查不能因为一次库抖动静默变成"全放行"（策略行缺失 ≠ 无策略） |
| L3 | 外部 API | **降级为仅本地结论**，`sources` 不写 `api` | 不留"api 已参与"的假象；不让外部不可用卡住审查 |

三条失败语义**方向不同**是刻意的：L1 失败往"松"走（漏审），L2 失败往"紧"走（按出厂策略办），
L3 失败往"不参与"走。混成一条"失败就全拦"或"失败就全放"，都会制造不可见的系统性偏差。

### 决策二：用户与商户是两条规则线，不是一个规则的两种参数

出厂口径（代码：`service.DefaultPolicy`）：

| | `user` | `merchant` |
|---|---|---|
| 审查场景 | `inbound_message` | `material` / `kb_document` / `outbound_reply` / `marketing_copy` |
| 拦截阈值 | sev ≥ 3 | sev ≥ 2 |
| 转人工阈值 | sev ≥ 2 | sev ≥ 1 |
| 拦截动作 | `reject` | `block_publish` |
| 临时冻结 | 24h | 7 天 |
| 永久升级 | 窗口内第 3 次 | 窗口内第 2 次 |

**为什么阈值方向相反（用户更松、商户更严）**：用户侧一次口无遮拦是常态，误杀成本（把正常客户冻一天）
远大于收益；商户侧对外内容一旦发出就收不回，且商户是经营主体、平台对它有处置权。

### 决策三：异步流水线 = 落库队列 + 进程内通知，业务侧只有一次插入

- `Submit` 的唯一同步 IO 是 `guard_tasks` 的一次插入，随后一次**非阻塞**通知（channel 满就丢，
  丢了最坏延迟一个轮询周期）。
- worker 每轮都**从表里认领**（`FOR UPDATE SKIP LOCKED`），因此：进程重启不丢在途任务、多副本不重复处理、
  通知丢失不影响正确性。
- 幂等键 `task_key = sha256(subject_type | subject_id | scene | content)`：上游重投、前端重发、
  重试都不会把同一条内容审两遍、罚两次；**主体进摘要**，所以两个主体各自的同一句话是两条任务（处罚分主体）。
- 失败语义**必须区分**：`MarkFailed(retryAt != 0)` ⇒ 回 `pending` 并顺延（积压数可见）；
  `MarkFailed(retryAt = 0)` ⇒ 置 `failed` 死信。把死信留在 `pending` 会让"积压数"永远清不掉，
  把可重试的置成 `failed` 会让一次抖动永久丢一条审查。

### 决策四：`trace_id` 只做关联，不承载审查

`trace_events` 是旁路可观测数据（best-effort、可丢、无全文）。本方案在任务与记录上都带 `trace_id`，
用途是"这条审查属于哪次请求"的回溯，**不是**任务载体。这条决策的代价是多一张表；收益是审查结论不会丢。

### 决策五：处置幂等、升不降、看时间不看定时任务

- **生效判定唯一口径**：`Active=true` 且（`permanent` 或 `ExpiresAt` 在未来）。不依赖任何定时任务。
- **幂等升不降**：同一主体重复命中只做"续期或升级"（temp → permanent），
  绝不因为一条新的临时记录把已有永久冻结降回临时（那等于给违规者自动减刑）。
- **解除立即生效**：`Apply`/`Release` 都主动失效热路径缓存（默认 TTL 5s），
  否则运营点了"解除"而用户还在被拦，会被当成系统坏了。
- **temp 档缺 `expires_at` 按永久处理**（fail-closed）：宁可让人工来解，也不让一条本该生效的处罚因字段缺失静默失效。

### 决策六：人工复核改判必须连带解除处置

`overturned` 时若该记录关联了自动处置，必须 `Release` 它。
只改记录不解冻，等于复核按钮是个安慰剂——误杀的代价不只是这一条内容被拦，而是这个人被冻结了一整天。

### 决策七：冻结要在用户可感知的地方生效（入站闸门）

冻结若只落一行 `Active=true`，用户照旧收到回复，等于罚了等于没罚。
本方案通过 `agent_runtime.SetGuardGate` 把 `Runtime.IsBlocked` 接到 Agent 入站处理链上：

- **用极小接口注册，而不是让 agent 域 import contentguard**：两个域的连接交给装配层（`internal/app`），
  agent 域不产生对审查域的编译期依赖，也不会循环引用；
- **未装配时是纯 no-op**：老部署行为逐字节不变；
- 命中冻结时**返回 nil 而不是 error**：冻结是预期状态，不是故障，不该进错误日志、更不该触发重试。

## 后果与局限

### 正面后果

- 内容审核的**正确性可离线测**：`service` 只依赖 `Store` 接口，测试用 `contentguard/memory` 装配，
  不连数据库（本功能 60+ 用例全部无外部依赖，`-race` 通过）。
- 业务链路零改动、零延迟影响：新增渠道只要发了 `customer.message.received`，自动进入审查队列。
- 可解释证据链：命中词 / 分类 / 严重级别 / **原文区间**（归一化索引回映射），脱敏后入库。
- 处置可审计：谁、何时、因为哪条记录、临时还是永久、谁解的、为什么解。

### 局限（明确的取舍，不要当成 bug）

1. **异步窗口内的首条消息可能已被回复**。判定是异步的，第一条违规消息可能已经发出去了；
   冻结对**后续**消息生效。若业务不可接受，高危场景（商户对外发布）可改用同步 `ScanNow` 前置校验。
2. **入口侧未真正拒收**：当前拒收落在"Agent 不生成回复"，消息本身仍由 webhook 落库（见调研 §7 差距 1）。
3. **繁简/拼音/形近字未归一化**：本地只做确定性字符变换，语义级变体交给 L3。
4. **云厂商签名适配未实现**：当前是通用 JSON-over-HTTP 契约，推荐用自家网关做协议翻译（一次适配、多租户复用）。
5. **管理前端页面未做**：只有后端 API 与文档；前端待建（含新手上路引导）。
6. **短词误杀**：纯子串 + 归一化无法解决"杀"命中"杀虫剂"，需运营用白名单或上下文规则兜（属运营口径）。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| 词库被误配置成"全拦"（如把单字高频词设 sev=3） | `/scan` 试算端点用**同一个引擎**验口径；策略 `block_severity` 越界自动回落出厂值 |
| 冻结后被误判（误杀） | 人工复核 `overturned` 连带解除；`review` 结论不处置只入队 |
| 外部 API 被误开启导致数据出域 | 双重显式（环境变量 + 策略）+ 主机白名单 + 禁重定向 + 响应体上限 + 强制 HTTPS（或显式 `AllowInsecure`） |
| 队列积压无人发现 | `CountPending` 进 `Stats`（运维面板/健康检查）；死信与积压分离显示 |
