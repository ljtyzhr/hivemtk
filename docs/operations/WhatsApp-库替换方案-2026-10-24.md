本仓同时存在两套互不相通的 WhatsApp 账号表：

|---|---|---|

| 登录方式 | 扫码（gowa） | 无登录概念，用长期 Token |
| 入站 Webhook | **未接线**（`webhookAccountTableByChannel` 对 WhatsApp 指向 `whatsapp_cloud_accounts`，`internal/service/webhook.go:431`） | 完整接线：验签、解析、落 `message_hub`、媒体转存 |
| 出站发送 | `WhatsappService`（草稿/群发） | `WhatsAppCloudIntegrationService`（AI 回复、`reach.whatsapp.send`、测试发送） |
| 会话持久化 | `whatsapp_sessions`（`internal/repository/whatsapp.go:20-21`、`:80-100`） | 无（API 无会话） |

两个关键事实：

1. `WhatsappService.providerFor` 的 Cloud 分支要求 `whatsapp_accounts` 行里 `Type=cloud` 且 `PhoneID/Token` 非空；但正常 API/UI **写不进这两个字段**。因此该分支实际只能靠手工改库触发，日常“创建账号 → 扫码登录 → 群发”走的是 legacy。
2. 入站与 AI 回复完全走 `whatsapp_cloud_accounts`；`whatsapp_accounts` 没有入站路径。也就是说，legacy 模块是**只出不进**的。

## 3. 能力缺口与影响面

### G1 账号供给缺口（P0，直接阻塞“删 gowa”）

`whatsapp_accounts` 的创建/更新接口只接受 `name/remark`，而 Cloud 分支要求 `PhoneID/Token` 非空。删除 gowa 后，现有“WhatsApp 账号管理”页创建的账号**没有任何合法的凭据写入路径**，发送会落到 `unavailable` 或报 `cloud api credentials missing`。

影响接口/页面：

- `POST/PUT /api/whatsapp/accounts`（`platform_routes.go:43-44`）
- `/whatsapp/account` 页面（`user-web/src/views/whatsapp/WhatsappAccount.vue`）
- 依赖账号列表的 `/api/whatsapp/group-messaging/send`、`/api/whatsapp/bulk-send`

### G2 扫码登录退场（P0，产品决策）

Cloud API 没有二维码登录。删除 gowa 等于删除“个人版账号扫码接入”这一产品能力。

影响接口/页面：

- `POST /api/whatsapp/accounts/:id/login/start`、`POST /api/whatsapp/start-login`
- `GET /api/whatsapp/accounts/:id/login/status` 中的 `qr` 字段
- `WhatsappAccount.vue` 的“登录/状态/二维码弹窗”
- `whatsapp_group_messaging.go:283-293` 的“无会话自动拉起扫码登录”分支

### G3 群发模板语义缺口（P0/P1，Cloud 下会直接失败）

现有群发把**本地模板**（`whatsapp_message_templates`）渲染成自由文本，再走 `SendTextMessage`。这在国内个人版场景可行，但 Cloud API 在 24h 客服窗口外**必须**使用 Meta 已审批模板（名称/语言/参数）。当前没有：

- 本地模板 → Meta 模板名/语言的映射；
- 发送前的 24h 窗口判断；
- 失败时的 Meta 错误码分类（底层 `core.APIError` 已带 `Code`，但群发只存 `err.Error()` 字符串）。

影响接口/页面：

- `POST /api/whatsapp/group-messaging/send`
- `POST /api/whatsapp/bulk-send`
- `POST /api/whatsapp/jobs`（`CreateBulkJob`）
- `user-web/src/views/whatsapp/BulkMatrix.vue`、`user-web/src/views/whatsappBot/BulkMessaging.vue`

### G4 出站媒体缺口（P1，非回归但需明示）

legacy 与 cloud 都**没有**出站媒体发送接线。删 gowa 不会让这项能力变差，但“全量 Cloud API”并不自动带来媒体发送；如果业务需要发图/文件，要另立切片实现上传媒体 + 发送消息。入站媒体转存不受影响。

### G5 双账号表并存（P1，长期债务）

`whatsapp_accounts` 与 `whatsapp_cloud_accounts` 字段、主键、状态语义都不同；两套凭证存储会增加轮换与审计成本。方案 A 的终态应合并到 `whatsapp_cloud_accounts`，但这是一次独立迁移，不应和“删 gowa”绑在同一刀里（否则回滚面过大）。

### G6 主动触达账号 ID 口径不一致（P1，既有缺陷）

- `ProactiveReachRepository.FindActiveAccountID` 对 `whatsapp` 查 `whatsapp_accounts` 并返回 UUID（`internal/repository/proactive_reach_repo.go:74-84`）；
- `ProactiveReachService.sendWhatsApp` 用 `parseUint` 转成 `uint`（`internal/service/proactive_reach.go:774-781`）；
- 发送侧 `WhatsAppCloudIntegrationService` 按 `uint` 查 `whatsapp_cloud_accounts`（`feishu.go:916-928`、`:1011-1019`）。

结果：**主动触达的 WhatsApp 腿在账号 ID 上就对不上**。这不是 gowa 引入的，但方案 A 收口账号表时应一并修掉，否则“只留 Cloud”后这条腿仍然不可用。

### G7 个人版入站从未接线（P2，无回归）

gowa 有能力收消息，但本仓没有任何 `AddHandler` 接线。删除它不会丢失现有入站能力；不要把它写成“换库导致收不到消息”。

### G8 文档与台账（P2，必须同批）

依赖基线、第三方许可证清单、LICENSE 合规说明、SBOM 都记录了 gowa。只删代码不删台账，门会红或留下假账（基线行不删会 `STALE`）。

## 4. 替换方案对比

### 方案 A：全量 Cloud API（推荐）

**做法**：业务只保留 Meta 官方 Cloud API；删除 `legacyWhatsAppProvider`、gowa 依赖、扫码登录入口；账号、群发、AI 回复统一走 Cloud。

**为什么推荐**：

- Cloud 已是官方合规路线，入站、验签、媒体、状态回执、模板、AI 回复都已接线；gowa 覆盖的“文本发送”Cloud 完全具备。
- gowa 上游 2021 年后停更，且个人版 Web 协议持续收紧；风险不是“有没有 CVE”，而是“随时整块失效”。
- A2-c 已把改动面收敛到一个文件，代码删除成本低；真正需要投入的是产品面与账号供给。

**代价**：

| 代价项 | 说明 | 档位 |
|---|---|---|
| 产品能力退场 | 失去个人版扫码接入；必须接受 WABA/商业号码 | 决策成本高 |
| 账号供给改造 | 必须给 `whatsapp_accounts` 补凭据字段，或整体切到 `whatsapp_cloud_accounts` | S（补字段）/ L（并表） |
| 群发语义改造 | 本地模板 → Meta 模板映射、24h 窗口判断、错误码入库 | M |
| 外部依赖 | WABA、号码、长期 Token、App Secret、模板审批、公网 HTTPS 回调 | 业务方提供 |
| 运营约束 | 24h 窗口、模板审核、限流/质量评级 | 持续运营成本 |

**分两阶段**：

- **A-1（最小可删）**：保留 `whatsapp_accounts`，补凭据写入 + 群发窗口/模板判断，然后删 gowa。优点是改动小、能最快让 gowa 归零；缺点是双账号表继续并存，且**同一套 WABA 凭据会存在两处**，轮换与审计成本上升。
- **A-2（终态）**：把 `WhatsappService` / 草稿 / 群发作业迁到 `whatsapp_cloud_accounts`，退役 `whatsapp_accounts` 与 `whatsapp_sessions`，同时修 G6。工作量大，单独切片。

### 方案 B：保持双 provider，换掉 gowa 的个人版实现

**做法**：把 `legacyWhatsAppProvider` 的内部实现从 gowa 换成维护中的个人版协议库（例如 `whatsmeow`，以实际选型与许可证评估为准），接口与上层不动。

**优点**：保留扫码登录与个人版账号；改动集中在 seam 一个文件。

**代价与风险**：

- 仍然是**非官方协议**，Meta 收紧时同样会失效；只是把“停更风险”换成“跟随维护风险”。
- 新库的登录/设备存储/重连模型与 gowa 不同，`StartLogin`、`warmConn`、会话存储都要重写；`whatsapp_sessions` 里的旧会话大概率不能直接迁移，需要重新扫码。
- 需要新增依赖与许可证评估；上线前要对二维码、断线重连、消息发送做真机回归。
- 工作量档位：M~L；且不解决 G1/G3 之外的合规问题（个人版仍非官方商业接入）。

**适用条件**：业务明确不能放弃个人版号码/扫码，且愿意承担协议风险。应把它定位为**有到期日的桥接**，而不是终态。

### 方案 C：暂不替换

**做法**：维持现状，依赖 seam 与依赖策略门继续观察，基线 review 日期为 `2027-03-31`。

**优点**：零改动、零业务影响。

**代价**：风险继续存在；到期必须做决定（换掉或显式延期并写理由）。只有在“业务尚未决定是否放弃个人版”时才成立，且应把决策日期写进台账。

### 推荐结论

**推荐 A（先 A-1，再 A-2）**，前提是业务确认“仅 Cloud API”可接受且能提供 WABA/号码/Token。若业务坚持个人版扫码，则选 B，但必须设到期日；C 只作为等待业务决策的过渡态，不作为长期方案。

## 9. 一页结论

- **现状**：gowa 只在 `whatsapp_provider.go`，共 1 文件 10 处代码引用；上层已接口化，但生产默认仍走个人版扫码与老式发送。
- **能力缺口**：Cloud 覆盖文本/模板/入站/媒体下载/状态回执；缺的是账号凭据供给（G1）、扫码退场（G2）、群发模板与窗口语义（G3）；出站媒体两边都没有（G4）。
- **推荐**：方案 A，先 A-1（补凭据 + 群发合规，删 gowa），再 A-2（并表、修主动触达 ID 口径）。
- **外部前提**：WABA、商业号码、长期 Token、App Secret、Verify Token、公网 HTTPS 回调、已审批模板、opt-in。
- **口径**：在 `go.mod/go.sum` 归零、源码零引用、Cloud 真实回执验收通过之前，**不得宣称“已替换”**。
